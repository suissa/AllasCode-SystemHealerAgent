# SystemHealerAgent — Causal Error-to-Configuration Examples

This document shows how the `SystemHealerAgent` should connect runtime evidence to a configuration cause before touching `configs/core.yml`.

The examples intentionally separate:

```text
Observed failure
!=
Configuration cause
```

A timeout, retry exhaustion, queue overflow, or circuit opening is only an observation. The SystemHealerAgent may intervene only after the CodeManager establishes a causal chain that makes a specific configuration value part of the mechanism.

---

## Example 1 — Retry storm caused by backoff below provider recovery window

### Runtime evidence

```text
Intent: Commerce.SyncCatalog
Action: Commerce.FetchCatalogPage

Events:
- Commerce.FetchCatalogPage.Error rate_limited
- Commerce.FetchCatalogPage.Error rate_limited
- Commerce.FetchCatalogPage.Error rate_limited
- Commerce.SyncCatalog.Error retry_exhausted

Metrics:
provider_retry_after_ms = 2000
configured_initial_backoff_ms = 50
configured_max_retries = 3
request_spacing_ms = [52, 101, 203]

Traces:
provider response 429 Retry-After=2000
runtime retry scheduled 50ms
provider response 429 Retry-After=2000
runtime retry scheduled 100ms

Logs:
Action returned the typed transient error correctly
runtime retry policy did not wait for provider recovery window

Error:
Catalog sync exhausted retries while provider continued rate limiting.
```

### Why this points to configuration

The Action is doing what its contract requires: it reports a transient `rate_limited` result and exposes the provider timing information.

The retries are generated by runtime policy, not by the Action implementation.

The critical causal relationship is:

```text
provider requires >= 2000ms
-> core retry policy schedules 50/100/200ms
-> each retry occurs inside the same throttle window
-> provider returns 429 again
-> retry budget is consumed
-> Intent fails
```

### System thesis

```text
The failure is caused by a retry/backoff configuration that re-enters the provider before the provider's declared recovery window has elapsed.
```

### Configuration target

Conceptually:

```yaml
retry:
  initial_backoff_ms: 50
  max_backoff_ms: ...
  respect_retry_after: false
```

The SystemHealerAgent may change only the authorized healable properties in `configs/core.yml`.

### Proposed intervention

Align retry scheduling with provider recovery hints, subject to local maximum safety bounds.

### Predicted effect

```text
retry spacing >= allowed provider window
-> no repeated request inside same throttle interval
-> retry budget is not consumed immediately
-> synchronization can resume after throttling clears
```

### Falsification

The thesis is wrong if:

- the Action is actually discarding required retry metadata;
- runtime already waits at least 2000ms;
- requests still fail identically after respecting the recovery window because the provider is permanently unavailable.

### Why CodeHealer must not be used

Changing `FetchCatalogPage/implementation.zig` would alter correct Action behavior to compensate for a runtime retry-policy defect.

## Example 2 — Valid operation killed by timeout that is shorter than normal completion time

### Runtime evidence

```text
Intent: Commerce.CloseSale
Action: Commerce.CommitLedger

Metrics:
action_timeout_ms = 500
p50_commit_ms = 420
p95_commit_ms = 790
p99_commit_ms = 860
failed_execution_commit_ms_before_cancel = 501

Trace:
CommitLedger start
DB transaction active
ledger write accepted
waiting for durable acknowledgement
runtime timeout at 500ms
Action cancelled

Logs:
no semantic validation error
no database constraint violation
no deadlock reported

Error:
CommitLedger exceeded action timeout.
```

### Causal chain

```text
configured timeout = 500ms
-> normal tail latency frequently exceeds 500ms
-> runtime cancels an otherwise valid operation
-> durable acknowledgement is not observed
-> Intent enters recovery
```

### System thesis

The configured timeout is below the valid operating envelope of the ledger commit path.

### Configuration target

```yaml
runtime:
  action_timeout_ms: 500
```

or, if scoped timeouts exist:

```yaml
actions:
  Commerce.CommitLedger:
    timeout_ms: 500
```

### Proposed intervention

Increase the healable timeout only enough to cover the measured valid completion window while remaining inside the SLO and safety ceiling.

### Predicted effect

The same operation should complete instead of being cancelled near 500ms.

### Falsification

Reject the thesis if traces show the operation is stalled rather than progressing, or if increasing the timeout only delays an inevitable failure.

### Important distinction

A timeout error alone does not prove a timeout configuration fault. The evidence must show that the operation is valid and still progressing when the configured boundary terminates it.

## Example 3 — Queue capacity is the binding constraint

### Runtime evidence

```text
Intent: Commerce.ImportOrders

Metrics:
queue_capacity = 100
queue_depth = 100
consumer_lag_ms = 35
consumer_error_rate = 0
incoming_burst = 180 items
rejected_items = 80

Events:
ImportOrders.Accepted x100
ImportOrders.Error queue_full x80

Logs:
consumer pool healthy
no downstream storage errors
```

### Causal chain

```text
incoming burst > configured queue capacity
-> queue reaches exactly 100
-> runtime admission refuses item 101+
-> healthy consumers never receive rejected items
-> Intent loses work
```

### System thesis

Queue admission failure is caused by a configured capacity that is below an expected valid burst, while downstream consumers remain healthy.

### Configuration target

```yaml
queue:
  capacity: 100
```

### Proposed intervention

Increase capacity within memory/resource budget bounds.

### Predicted effect

A valid burst that previously produced `queue_full` should be accepted without changing Action semantics.

### Falsification

If larger capacity only moves the failure downstream and consumer lag grows without bound, capacity was not the root cause; it was masking insufficient processing throughput.

### Key lesson

SystemHealer must not equate `queue_full` with “increase the queue.” It must verify that capacity itself is the binding constraint rather than a symptom of downstream saturation.

## Example 4 — Excess worker concurrency overwhelms a smaller DB pool

### Runtime evidence

```text
workers = 64
db_pool_size = 16

Metrics:
active_workers = 64
active_db_connections = 16
workers_waiting_for_db = 43
request_p95_ms rises from 120 to 1900
DB CPU = 42%
DB lock contention = low

Traces:
worker spans spend most time waiting for connection acquisition
```

### Causal chain

```text
64 concurrent workers
-> only 16 DB connections available
-> workers queue for connections
-> waiting time dominates end-to-end latency
-> Action timeouts begin
```

### System thesis

Configured worker concurrency exceeds the bounded downstream connection capacity, amplifying queueing latency into timeouts.

### Possible configuration interventions

There are two plausible system levers:

```yaml
runtime:
  workers: 64

database:
  pool_size: 16
```

The SystemHealerAgent should not change both blindly.

The CodeManager should determine which intervention is safer based on resource evidence.

If DB utilization is low and more connections are safe, pool size may be the intervention.

If DB has a hard connection budget, worker concurrency should be reduced instead.

### Predicted effect

The ratio between runnable work and available DB capacity should become compatible, reducing connection wait time and eliminating secondary timeouts.

### Falsification

If connection acquisition wait remains high despite balanced concurrency, the causal model is incomplete.

## Example 5 — Circuit breaker threshold below expected transient burst

### Runtime evidence

```text
circuit.failure_threshold = 3
circuit.open_duration_ms = 30000

Provider behavior:
short transient bursts of 3-4 failures during deployment
successful responses resume within ~800ms

Observed:
3 failures
-> circuit opens for 30s
-> thousands of requests rejected locally
-> provider had already recovered
```

### Causal chain

```text
normal transient burst reaches threshold
-> circuit opens
-> runtime blocks healthy requests for 30s
-> local policy creates longer outage than remote fault
```

### System thesis

The configured circuit-breaker sensitivity converts a short recoverable provider disturbance into prolonged local unavailability.

### Configuration target

```yaml
circuit_breaker:
  failure_threshold: 3
  open_duration_ms: 30000
```

### Intervention

Adjust the healable threshold/window combination within resilience policy bounds.

### Predicted effect

Short expected bursts should no longer create a long local outage, while sustained failures must still open the circuit.

### Falsification

If the provider failures are sustained rather than transient, raising the threshold would weaken protection and the thesis is invalid.

## Example 6 — Lease expires during valid processing

### Runtime evidence

```text
lease_duration_ms = 5000
p95_job_duration_ms = 7200
p99_job_duration_ms = 9100

Trace:
worker A acquires lease
worker A continues processing
lease expires at 5s
worker B acquires same work
both workers complete side effects

Error:
duplicate execution detected
```

### Causal chain

```text
lease shorter than legitimate job duration
-> lease expires while original worker is alive
-> work is reassigned
-> concurrent duplicate execution occurs
```

### System thesis

Lease duration is inconsistent with measured legitimate processing duration.

### Configuration target

```yaml
leases:
  duration_ms: 5000
```

### Intervention

Increase lease duration or, if the configuration supports it, enable/adjust lease renewal cadence.

### Predicted effect

A healthy worker should retain ownership for the full valid job duration.

### Falsification

If the first worker stopped heartbeating or lost ownership due to a real failure, extending the lease can worsen recovery time and is not justified.

## Example 7 — Cache TTL causes stale authority violation

### Runtime evidence

```text
cache_ttl_ms = 60000
required_freshness_ms = 5000

Event:
Product.PriceUpdated version=82

Trace:
write authority commits version 82
read request 18s later
cache returns version 81

Logs:
cache entry valid under configured 60s TTL
```

### Causal chain

```text
TTL permits 60s staleness
-> domain/read invariant permits only 5s
-> cache legally serves stale value under current config
-> user sees obsolete projection
```

### System thesis

The cache freshness policy is incompatible with the declared read freshness requirement.

### Configuration target

```yaml
cache:
  ttl_ms: 60000
```

### Predicted effect

Stale responses beyond the allowed freshness window should disappear.

### Falsification

If cache invalidation events are required by contract but are not emitted/consumed, the problem may instead be code/event handling, not TTL.

## Example 8 — Snapshot cadence produces unacceptable recovery cost

### Runtime evidence

```text
snapshot_every = 10000 events
recovery_target_ms = 2000
actual_recovery_ms = 8700
replayed_events = 9341
```

### Causal chain

```text
large snapshot interval
-> restart requires replay of thousands of events
-> recovery exceeds target
-> service remains unavailable longer than allowed
```

### System thesis

Snapshot cadence is too sparse for the declared recovery objective under current event volume.

### Configuration target

```yaml
event_store:
  snapshot_every: 10000
```

### Intervention

Reduce the interval within storage/write-amplification bounds.

### Predicted effect

Restart should replay fewer events and recover within target.

### Falsification

If replay itself is abnormally slow because of implementation defects, changing snapshot cadence only masks the real cause.

## Example 9 — Health-check threshold causes false eviction

### Runtime evidence

```text
health_check_timeout_ms = 100
normal_health_p95_ms = 140
normal_health_p99_ms = 190

Observed:
healthy instances repeatedly marked unhealthy around 100ms
load balancer removes them
remaining instances overload
```

### Causal chain

```text
health timeout < normal healthy response tail
-> healthy instances are falsely classified as failed
-> capacity is removed
-> load concentrates on remaining nodes
-> cascading latency begins
```

### System thesis

The health-check timeout is incompatible with normal healthy latency and causes false-positive failure detection.

### Configuration target

```yaml
health:
  timeout_ms: 100
```

### Predicted effect

Healthy instances should stop flapping while genuinely unresponsive instances still fail health checks.

### Falsification

If the slow health response is itself caused by an unhealthy application state, relaxing the timeout would hide the fault.

## Example 10 — Unknown: generic I/O error with insufficient evidence

### Runtime evidence

```text
Action: Commerce.StoreReceipt
Event: Commerce.StoreReceipt.Error unknown_io
Trace: store open target -> EIO
Disk free: 71%
First occurrence: yes
Kernel/storage diagnostics: unavailable
```

### Why SystemHealer must NOT change configuration

A generic `EIO` is compatible with multiple causes:

- device/filesystem fault;
- mount/runtime issue;
- invalid write sequence in Action implementation;
- transient host failure;
- storage adapter defect.

There is no discriminating causal evidence for a specific `configs/core.yml` value.

### Correct disposition

```text
fault_class = unknown
mutation_scope = none
next_step = bounded diagnostic replay / acquire storage evidence
```

This is a successful healing decision because refusing speculative mutation preserves causal attribution.

# How the agent connects an error to configuration

The SystemHealer architecture should use the following reasoning sequence.

## 1. Identify the failing boundary

Use the full Intent topology to determine where the observed failure emerges.

```text
Which Action/runtime stage failed?
What succeeded immediately before it?
What downstream effects occurred?
```

## 2. Determine whether the Action satisfied its contract

If the Action emitted the correct typed error/result and its local semantics are consistent with its contract, the evidence shifts toward a system fault.

If the Action produced an invalid value or violated its own postcondition, route toward CodeHealer instead.

## 3. Find the runtime policy that governs the observed mechanism

Examples:

```text
repeated too-early retries -> retry/backoff policy
termination at fixed duration -> timeout policy
rejection at exact depth -> queue capacity
waiting on scarce resource -> concurrency/pool limits
premature reassignment -> lease policy
false failure classification -> health threshold
stale-but-valid cached value -> TTL policy
slow replay after restart -> snapshot cadence
```

This maps an observed mechanism to a configuration dimension, not yet to a final solution.

## 4. Compare configured value with measured operating evidence

The agent should look for a contradiction such as:

```text
configured timeout < valid observed duration
configured retry delay < external recovery window
configured capacity < valid expected burst
configured concurrency > bounded downstream capacity
configured TTL > declared freshness requirement
configured lease < healthy processing duration
```

This is the main bridge between telemetry and configuration causality.

## 5. State alternatives

At least one plausible competing explanation should be considered.

Examples:

```text
Timeout too short
vs
operation is actually deadlocked

Queue too small
vs
consumers are too slow

TTL too long
vs
invalidation event is broken

Lease too short
vs
worker lost heartbeat
```

## 6. Define falsification before mutation

The thesis must predict what would prove it wrong.

## 7. Select the smallest bounded intervention

Prefer one causal dimension at a time.

## 8. Predict observable consequences

The expected result should be measurable in events, metrics, traces, logs, or acceptance behavior.

## 9. Let independent verification decide

The SystemHealerAgent does not promote its own change.

# Anti-patterns

The following behaviors are forbidden.

## Error-name matching

```text
error contains "timeout"
-> blindly increase timeout
```

This is correlation without mechanism.

## Multi-knob healing

```text
increase timeout
increase retries
increase workers
increase queue
```

This destroys causal attribution.

## Semantic weakening

Changing configuration so that an invariant is no longer checked is not healing.

## Code compensation

A system fault must not be hidden by changing `implementation.zig`.

## Test-targeted configuration

A value must not be selected merely because it passes a visible test. It must be justified by the causal thesis and survive hidden full-flow validation.

## Mutation under uncertainty

When the evidence does not distinguish code/system causes, the correct output is `unknown`, not a speculative configuration edit.
